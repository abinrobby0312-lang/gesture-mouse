# Gesture Mouse site

The landing page at **https://abinrobby0312-lang.github.io/gesture-mouse/** —
plain HTML, CSS and a little JavaScript. No build step, no trackers, no
third-party scripts. Colours follow `brand/BRAND.md`.

| File | What it is |
|---|---|
| `index.html` | Landing page: download, features, interactive install steps, FAQ, sign-up, contact |
| `report.html` | Compatibility form. The app opens it with the phone's details in the query string. |
| `privacy.html` | Privacy policy — update its date whenever what's collected changes |
| `config.js` | Settings: Supabase URL + anon key |
| `assets/release.json` | The version the download button offers — update it with each release |
| `supabase/schema.sql` | Database for the forms, download counts and the app's bug reports |
| `assets/*` | Generated by `brand/tools/site_assets.py` (logo, icons, social preview, QR) |

## Preview locally

```
python -m http.server 8765 --directory site
```

then open http://localhost:8765.

## Deploy

The site is served from the `gh-pages` branch, which holds only the contents of
this folder. To publish changes:

```
git subtree split --prefix site -b site-publish
git push origin site-publish:gh-pages --force
git branch -D site-publish
```

GitHub Pages rebuilds within a minute or two. Pages lets browsers cache files
for 10 minutes, so before deploying a change to `site.js`, `site.css` or
`config.js`, bump the `?v=` on their links in the three HTML files:

```
V=$(date +%Y%m%d%H%M); sed -i -E "s#\?v=[0-9]+#?v=$V#g" site/*.html
```

## Releasing a new app version

1. Bump `versionCode` / `versionName`, build on the machine with the release
   keystore, copy to `dist/`, write the `.sha256`.
2. Create a GitHub release tagged `vX.Y.Z` with the APK attached as
   **`GestureMouse.apk`** (always that name, so
   `/releases/latest/download/GestureMouse.apk` keeps working), with the
   SHA-256 in the notes.
3. Update `assets/release.json` — version, size in bytes, SHA-256, the
   release's download URL and notes URL — and redeploy the site.
4. Email the update list.

The page deliberately doesn't ask GitHub's API what's latest: it's
rate-limited per IP, and mobile carriers put thousands of people behind one.

## Forms (Supabase)

1. Create a Supabase project (free plan is plenty).
2. Run `supabase/schema.sql` in its SQL editor. Anonymous visitors can then
   *insert* into `signups`, `compat_reports` and `feedback`, and nothing else.
3. Put the project URL and the **anon / publishable** key in `config.js`, and
   redeploy. Never the service-role key.

Read entries in the Supabase dashboard (Table editor). Until `config.js` has
both values the forms say "Opening soon" instead of failing.

## Compatibility reports

Reports land in `compat_reports` with `reviewed = false`. They're used to find
and fix problems on particular phones and are **not published anywhere** — the
privacy policy says so, so keep it that way or change the policy first.

## Bug reports

The app's **Report a bug** button sends reports straight to the `bug_reports`
table, not through the site. The key inside the app can add rows and nothing
else, so they're readable only by us.

- **Read them:** Supabase dashboard → gesture-mouse → Table Editor →
  `bug_reports`, or ask Claude to "check bug reports". Each row has the app
  version, Android version, phone model, an optional note and email, and the
  scrubbed log. Tick `handled` when dealt with.
- **Delete them** once fixed, or when someone asks — the privacy policy
  promises both: `delete from public.bug_reports where handled;`
- **Limits:** 64 KB per report and 60 an hour in total. A flood uses up the
  hour's quota and later reports are refused until it passes, so if reports
  suddenly stop arriving, check the table.
- **Reading a log:** `GMouse` is the app's tag. The `state=`, `connect attempt`
  and `giving up` lines tell the connection story; computers appear as
  `computer-N` and Bluetooth addresses as `device-N`.
